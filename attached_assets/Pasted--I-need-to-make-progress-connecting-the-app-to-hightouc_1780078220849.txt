  Three concrete next moves, in priority order

  1. Pull and add the secret in Replit (5 min).

  Open the Repl shell:
  git fetch origin main && git reset --hard origin/main
  
  Then in Replit Secrets, add HIGHTOUCH_API_KEY with any strong random value (e.g., openssl rand -hex 32 in your local terminal). Restart the workflow. The integration is now live on your public Replit URL.

  2. Smoke test locally (5 min).

  export HIGHTOUCH_API_KEY="<the_secret>"
  curl -s -X POST https://<your-repl-url>/integrations/hightouch/brief \
    -H "Authorization: Bearer <the_secret>" \
    -H "Content-Type: application/json" \
    -d @docs/hightouch_sample_brief.json | jq

  You should get a 201 with a new sprint_id. Hit it again with the same payload and you get a 200 with duplicate: true and the same sprint_id — proving idempotency works. Then visit /sprints/<id>/chat and the chat UI loads bound to that sprint, exactly
  like a form-submitted one.

  3. Send the spec doc to Upwork's data team (15 min).

  docs/hightouch_integration.md is written to be sent verbatim. It tells them:
  - What endpoint to configure (custom HTTP destination in Hightouch)
  - What auth to use (Bearer + the shared HIGHTOUCH_API_KEY you generate)
  - Exact payload schema (every field, every enum value, every required vs optional)
  - Example payloads (minimal + realistic)
  - Response shapes for each status code
  - The four things they need to coordinate with you (API key sharing, host URL, rate limits, notification path)
  
  That doc is the actual "make progress connecting" deliverable. Once they have it, they can scope the warehouse-side work on their end (audience-table models, sync schedule, column mapping). Until they do that, the endpoint just waits.

  What's deliberately NOT in scope here

  - Outbound (ADAM → Hightouch). Today's integration is one-way: warehouse triggers a sprint. The reverse (ADAM sprint output flowing back to the warehouse for performance attribution) is a separate piece — needs a database write or a queryable API
  endpoint. Add later if/when Upwork wants closed-loop reporting.
  - HMAC request signing. Bearer token is sufficient for v1. If Upwork's security team requires per-row signature verification, we add it.
  - Job queue. Pipeline still runs in a subprocess from the request handler. Fine at <1 sprint/min. At higher volume the host needs a real queue (Redis, Celery, etc.). Hightouch's rate limit can throttle until that's built.
